# Kernel Loading and Execution

<!-- md-trans-meta sourceCommit=c984fae7c73f88f7e9e16b034bea72bc18e7517c translatedAt=2026-10-16T10:13:57.970Z pushedAt=2026-10-19T09:05:02.680Z -->

This topic describes how to load and execute custom kernels developed with Ascend C. **The APIs described in this topic need to be called only when you write your own operator kernels or need to directly control kernel binary loading, parameter assembly, and task dispatch.** If your service does not write operators and only invokes the operator capabilities already provided by CANN, you should preferentially call the aclnn operator APIs, such as **aclnnAdd**. The aclnn APIs encapsulate operator selection, parameter processing, kernel loading, and execution. You usually do not need to call the LaunchKernel APIs directly.

Custom kernels can be dispatched in two main methods:

- **Mixed programming**: Use the `<<< >>>` syntax directly in the host code to dispatch the kernel.
- **Non-mixed programming**: First compile the kernel into a standalone operator binary, and then load and dispatch it through Runtime APIs such as **aclrtBinaryLoadFromFile**, **aclrtBinaryGetFunction**, and **aclrtLaunchKernelWithConfig**.

## Differences Between the Two Methods

| Comparison Item | Mixed Programming: `<<< >>>` | Non-Mixed Programming: LaunchKernel API |
| --- | --- | --- |
| Kernel reference method | The host code directly references the kernel function symbol, for example, `add_custom<<<...>>>(...)`. | The host code obtains the **aclrtFuncHandle** by the kernel name string, for example, `aclrtBinaryGetFunction(bin, "add_custom", &func)`. |
| Compilation method | The kernel source code participates in the host project build. A linkable kernel library is usually generated through the Ascend C CMake capability and linked together with the host executable. | The kernel source code is compiled separately into an operator binary file, for example, `*.o` or fatbin. The host program is compiled separately and loads the binary at runtime through Runtime APIs. |
| Code generation | The build system generates the host-side callable kernel launch stub, registration information, and device-side code binding relationship, so that the `<<< >>>` syntax can directly dispatch tasks. | No directly callable Kernel launch stub is generated. The host side only stores the binary path, kernel name, and runtime handle. The binary must be loaded, the function obtained, and the parameters assembled manually. |
| Runtime loading | The kernel binary is usually registered together with the host program or the link library, and registration and loading are completed by the generated code upon the first dispatch. | The user explicitly calls **aclrtBinaryLoadFromFile** or **aclrtBinaryLoadFromData** to load the binary, and calls **aclrtBinaryUnLoad** to unload it at the end. |
| Parameter organization | Parameters are passed in the form of a function call, making the code concise and readable. | Parameters can be organized using the device parameter area, host parameter area, **aclrtArgsHandle** parameter list, placeholder, and other methods, providing finer control granularity. |
| Applicable scenario | The kernel and the host program are developed and released together, and the kernel set is determined at compile time. | The kernel binary needs to be released independently, selected dynamically, loaded lazily, or requires capabilities such as runtime parameter assembly, placeholder, and task attribute configuration. |

Under both methods, kernel task execution is asynchronous relative to the host thread after dispatch. If the host thread needs to wait for kernel execution to complete, it must call **aclrtSynchronizeStream**, **aclrtSynchronizeDevice**, or use synchronization mechanisms such as **Event**.

## Mixed Programming

In mixed programming, the host code can directly call the kernel function and use the `<<< >>>` syntax to specify the number of blocks, dynamic shared memory parameters, and stream for the task. This approach yields the most concise code and is suitable for scenarios where the kernel and host programs are released together.

During compilation, the kernel source code participates in the build as part of the project. For example, in the sample, the Ascend C CMake capability can be used to compile the kernel source code into a static library, which is then linked to the host executable.

```cmake
include(${ASCENDC_CMAKE_DIR}/ascendc.cmake)
ascendc_library(kernels STATIC kernel_print.cpp)

add_executable(main main.cpp)
target_link_libraries(main PRIVATE kernels ${ASCEND_CANN_PACKAGE_PATH}/lib64/libacl_rt.so)
```

The host-side code generated by the preceding approach can directly call the kernel launch function, so users do not need to explicitly call APIs such as **aclrtBinaryLoadFromFile** and **aclrtBinaryGetFunction**.

The key code example is as follows. It is for reference only and cannot be directly copied, compiled, or run.

```c
// Device code
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z)
{
    KernelAdd op;
    op.Init(x, y, z);
    op.Process();
}

int main()
{
    int64_t n = ...;
    size_t size = static_cast<size_t>(n) * sizeof(uint64_t);

    aclInit(nullptr);
    aclrtSetDevice(0);

    aclrtStream stream = nullptr;
    aclrtCreateStream(&stream);

    void *hX = nullptr;
    void *hY = nullptr;
    void *hZ = nullptr;
    aclrtMallocHost(&hX, size);
    aclrtMallocHost(&hY, size);
    aclrtMallocHost(&hZ, size);

    // Initialize the input data.
    ...

    void *dX = nullptr;
    void *dY = nullptr;
    void *dZ = nullptr;
    aclrtMalloc(&dX, size, ACL_MEM_MALLOC_HUGE_FIRST);
    aclrtMalloc(&dY, size, ACL_MEM_MALLOC_HUGE_FIRST);
    aclrtMalloc(&dZ, size, ACL_MEM_MALLOC_HUGE_FIRST);

    aclrtMemcpy(dX, size, hX, size, ACL_MEMCPY_HOST_TO_DEVICE);
    aclrtMemcpy(dY, size, hY, size, ACL_MEMCPY_HOST_TO_DEVICE);

    uint32_t numBlocks = 48;
    add_custom<<<numBlocks, nullptr, stream>>>(dX, dY, dZ);
    aclrtSynchronizeStream(stream);

    aclrtMemcpy(hZ, size, dZ, size, ACL_MEMCPY_DEVICE_TO_HOST);
    ...
}
```

## Non-Mixed Programming

In non-mixed programming, the device-side kernel code is first compiled into an independent operator binary. When the host program runs, it explicitly loads the binary, obtains the kernel function handle, assembles the parameters, and then calls the LaunchKernel API to dispatch the task.

During compilation, the kernel source code and the host program can be built separately. For example, in the sample, **ascendc_fatbin_library** can be used to generate the operator binary file, which is then loaded by the host program at runtime.

```cmake
include(${ASCENDC_CMAKE_DIR}/ascendc.cmake)
ascendc_fatbin_library(ascendc_kernels_simple add_custom.cpp)

add_executable(ascendc_kernels_bbit main.cpp)
target_link_libraries(ascendc_kernels_bbit PRIVATE ${ASCEND_CANN_PACKAGE_PATH}/lib64/libacl_rt.so)
```

The generated operator binary file is loaded through a path at runtime, for example, `./out/fatbin/ascendc_kernels_simple/ascendc_kernels_simple.o`. In this mode, the host code does not directly reference the kernel function symbol; instead, it operates the kernel through the binary and function handles.

The related concepts are as follows:

- **Binary**: A dynamically loaded code container unit that contains the compiled kernel code, global variables, and so on. Users load the operator binary through **aclrtBinaryLoadFromFile** or **aclrtBinaryLoadFromData** and obtain the binary handle.
- **Function**: A specific executable kernel entry inside a binary. Users obtain the function handle through **aclrtBinaryGetFunction** or **aclrtBinaryGetFunctionByEntry**.
- **Parameter list**: Kernel parameters that the LaunchKernel API needs to obtain. The parameters can be placed in device memory, host memory, or an **aclrtArgsHandle** parameter list. You can also use a placeholder to let Runtime transfer small blocks of parameter data during launch.

The following is a key code example that uses the LaunchKernel API. It cannot be directly copied, compiled, and run, and is for reference only.

```c
// Device code, compiled into an independent operator binary file.
extern "C" __global__ __aicore__ void add_custom(GM_ADDR x, GM_ADDR y, GM_ADDR z)
{
    KernelAdd op;
    op.Init(x, y, z);
    op.Process();
}

int main()
{
    int64_t n = ...;
    size_t size = static_cast<size_t>(n) * sizeof(uint64_t);

    aclInit(nullptr);
    aclrtSetDevice(0);

    aclrtStream stream = nullptr;
    aclrtCreateStream(&stream);

    // Load the operator binary and obtain the kernel function handle.
    aclrtBinHandle bin = nullptr;
    aclrtBinaryLoadFromFile("add_custom.o", nullptr, &bin);

    aclrtFuncHandle func = nullptr;
    aclrtBinaryGetFunction(bin, "add_custom", &func);

    void *hX = nullptr;
    void *hY = nullptr;
    void *hZ = nullptr;
    aclrtMallocHost(&hX, size);
    aclrtMallocHost(&hY, size);
    aclrtMallocHost(&hZ, size);

    // Initialize the input data.
    ...

    void *dX = nullptr;
    void *dY = nullptr;
    void *dZ = nullptr;
    aclrtMalloc(&dX, size, ACL_MEM_MALLOC_HUGE_FIRST);
    aclrtMalloc(&dY, size, ACL_MEM_MALLOC_HUGE_FIRST);
    aclrtMalloc(&dZ, size, ACL_MEM_MALLOC_HUGE_FIRST);

    aclrtMemcpy(dX, size, hX, size, ACL_MEMCPY_HOST_TO_DEVICE);
    aclrtMemcpy(dY, size, hY, size, ACL_MEMCPY_HOST_TO_DEVICE);

    uint32_t numBlocks = 48;
    void *args[] = {dX, dY, dZ};
    size_t argsSize = sizeof(args);
    aclrtLaunchKernelWithHostArgs(func, numBlocks, stream, nullptr, args, argsSize, nullptr, 0);
    aclrtSynchronizeStream(stream);

    aclrtMemcpy(hZ, size, dZ, size, ACL_MEMCPY_DEVICE_TO_HOST);

    aclrtBinaryUnLoad(bin);
    ...
}
```

The following describes how to select an API from the LaunchKernel API family.

| API | Parameter Source | Applicable Scenario |
| --- | --- | --- |
| aclrtLaunchKernel | Complete parameter area in device memory | Parameters have been assembled on the device side, and no launch configuration is required. |
| aclrtLaunchKernelV2 | Complete parameter area in device memory | An additional launch configuration needs to be specified. |
| aclrtLaunchKernelWithConfig | **aclrtArgsHandle** parameter list | You want Runtime to manage the parameter layout, or you need capabilities such as placeholders and parameter updates. |
| aclrtLaunchKernelWithHostArgs | Complete parameter area in host memory | Parameters are organized contiguously on the host side and processed by Runtime at launch. |
| aclrtLaunchKernelWithArgsArray | Host-side parameter array | Each array element points to a parameter data item, facilitating invocation organized in the form of a parameter array. |

For a complete sample, see [0_launch_kernel](../../../example/2_advanced_features/kernel/0_launch_kernel/README_en.md). This sample demonstrates the binary loading, function obtaining, **aclrtArgsHandle** parameter assembly, placeholder parameters, and **aclrtLaunchKernelWithConfig** launch process.
