# Viewing Logs (Ascend EP)

<!-- md-trans-meta sourceCommit=490980fac47f296083b7cdba2f59604a84255da6 translatedAt=2026-10-22T09:36:49.411Z pushedAt=2026-10-23T09:14:13.310Z -->

This topic describes the storage paths of log files and the main information recorded in each log file in Ascend EP mode.

## Viewing Application Logs

Application logs record the logs generated by running applications. For example, after an AscendCL application finishes running, you can view the application logs in **"$HOME/ascend/log"** by default.

The following describes application logs:

- Application logs can be viewed in a container or on a physical machine. To ensure that the log tool runs properly in a container, you need to map the path of the log tool dynamic library file **libascendalog.so** and its dependent **libc\_sec.so** to the container. The paths are "`${INSTALL_DIR}/compiler/lib64/libascendalog.so`" and "`${INSTALL_DIR}/driver/lib64/common/libc_sec.so`", respectively. For operations in a container, see [CANN Software Installation](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/920/softwareinst/instg/instg_0000.html?OS=openEuler&InstallType=netyum).

  Replace **$\{INSTALL\_DIR\}** with the file storage path after CANN software installation. For example, if you install the software as the **root** user, the default file storage path is **/usr/local/Ascend/cann**.

- Application logs on the device side are automatically sent to the host side. If the sending fails, the logs are directly stored to the disk on the device side. If the sending succeeds, the logs are not stored to the disk on the device side.
- Application logs support aging. If the number or size of log files exceeds the limit, the earliest log directory or file is automatically deleted. For the configuration of the number or size of log files, see the environment variable [ASCEND\_HOST\_LOG\_FILE\_NUM](../env_vars/ASCEND_HOST_LOG_FILE_NUM.md).

```sh
├── debug
│   ├── device-0
│   │   ├── device-2272_20220617234019449.log
│   │   └── device-6564_20220617232348429.log
│   └── plog
│       └── plog-16027_20220618001623878.log
├── run
│   ├── device-0
│   │   ├── device-2272_20220617234019449.log
│   │   └── device-6564_20220617232348429.log
│   └── plog
│       └── plog-16027_20220618001623878.log
└── security
    ├── device-0
    │   ├── device-2272_20220617234019449.log
    │   └── device-6564_20220617232348429.log
    └── plog
        └── plog-16027_20220618001623878.log
```

**Table 1**  Application log description

|Storage Path|Description|
|--|--|
|`$HOME/ascend/log/debug/device-id/device-pid_*.log`|Debug logs generated by running applications on the device side, mainly including logs of modules such as AI CPU and HCCP on the device side.|
|`$HOME/ascend/log/debug/plog/plog-pid_*.log`|Debug logs generated by running applications on the host side. They mainly include logs of compiler components (such as GE, FE, AI CPU, TBE, and HCCL), runtime components (such as AscendCL, GE, and Runtime), and driver user-mode logs.|
|`$HOME/ascend/log/run/device-id/device-pid_*.log`|Run logs generated by running applications on the device side.|
|`$HOME/ascend/log/run/plog/plog-pid_*.log`|Run logs generated by running applications on the host side.|
|`$HOME/ascend/log/security/device-id/device-pid_*.log`|Security logs generated by running applications on the device side.|
|`$HOME/ascend/log/security/plog/plog-pid_*.log`|Security logs generated by running applications on the host side.|

Note 1: In the preceding logs, `id` and `pid` represent the device ID and service process ID respectively, subject to the actual values. The **"\*"** in the log file name indicates the timestamp when the log file is created.

Note 2: The preceding directories are shared by all applications in the container or on the physical machine. As new application processes are continuously added, logs keep increasing. Therefore, users need to clean up these directories periodically. Otherwise, insufficient disk space may occur and affect normal service running.

Note 3: If logs are stored on media with a limited number of writes, such as emmc/flash, it is recommended that the log storage-to-disk path be set to a path in the memory file system. When starting a service process, set the log storage-to-disk path through the environment variable **ASCEND\_PROCESS\_LOG\_PATH**. You can also start a resident process to periodically dump logs from the memory file system to `emmc/flash` in batches. For details, see [Environment Variable Reference](https://gitcode.com/cann/docs/blob/9.2.0/docs/en/env-vars/README.md).

Note 4: In a container, `device-id` in the directory indicates a logical ID.

Other related configurations:

- **Modifying the storage-to-disk path of application logs**: You can use the environment variable **ASCEND\_PROCESS\_LOG\_PATH** to specify the log storage-to-disk path. If developers expect files generated during compilation and running to be stored to a unified path, they can use **ASCEND\_WORK\_PATH** to set the storage path of files exclusive to a single device.
- **Setting the sending delay of device-side application logs**: In the standard Ascend EP form, the **slogd** process on the device side automatically sends device-side application logs to the host side, so that users can directly view device-side application logs on the host side. Before a service process exits, the system has a default delay of 2000 ms to send device-side application logs to the host side. After the timeout, the service process exits. Logs that are not sent to the host side are directly stored to disk on the device side. You can use the environment variable **ASCEND\_LOG\_DEVICE\_FLUSH\_TIMEOUT** to set a longer delay for sending device-side application logs to the host side.
- **Setting the number of log files stored for each process in the application log directories (plog and device-id)**: The number of log files sent by a single process that can be stored in the `plog` and `device-id` log directories is 10 by default. This number can be set through the environment variable **ASCEND\_HOST\_LOG\_FILE\_NUM**.
- **Specifying the log congestion handling mode**: In the case of log congestion or poor I/O access performance, the system may lose logs to ensure that service performance does not degrade. To facilitate problem locating, users can set **ASCEND\_LOG\_SYNC\_SAVE** to prevent log loss in the case of log congestion or poor I/O access performance.
- **Setting the log display mode**: By default, logs are saved to log files. If logs need to be printed, you can set the environment variable **ASCEND\_LOG\_PRINT\_TO\_STDOUT**. After the log printing feature is enabled, you can also save logs to a specified file through output redirection when starting an application process, for example, **./main \> log.txt**

Note: For details about the preceding environment variables, see [Environment Variable Reference](https://gitcode.com/cann/docs/blob/9.2.0/docs/en/env-vars/README.md).

## Viewing System Logs

System logs are used to record system running information. In the standard Ascend EP form, users do not have the login permission for the device. Therefore, the msnpureport tool is required to transfer the system logs on the device side to the host side for viewing. For details, see [msnpureport Tool Usage Guide](https://support.huawei.com/enterprise/en/ascend-computing/ascend-hdk-pid-252764743?category=reference-guides&subcategory=command-reference).

The system logs are described as follows:

- Viewing system logs on the device side is not supported in containers, and exporting system logs on the device side through the msnpureport tool is not supported either.
- System logs support aging. If the number or size of log files exceeds the limit, the earliest log directory or file is automatically deleted.
